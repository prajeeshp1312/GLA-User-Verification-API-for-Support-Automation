Product requirements

GLA User Verification API for Support Automation

Before any reply is drafted, check that the sender is a real, active GLA user. Everyone else is stopped before the AI step and before a draft exists.

17 Nov 2026Prajeesh Pacademy@greatlearning.in
1

Overview

Before the support automation drafts any reply, it checks through an API that the sender is a real, active GLA user. Only verified senders continue through the flow.

Today every new email in academy@greatlearning.in is classified by the AI and gets a draft. Nothing checks who the sender is, so anyone outside GLA can send bulk or scam mail and fill the mailbox with drafts, using up AI calls and n8n executions. This PRD covers the verification step and the API behind it, up to the point where n8n receives the API result.

2

Problem and goals

The problem. The current system is vulnerable to cyber attack. Anyone looking for a loophole can send a large number of scam emails from many different accounts. Every one is classified by the LLM and gets a draft, so an attacker can burn AI budget and flood the mailbox. Nothing checks that the sender is a real GLA learner.

Goals
  • Only emails from verified GLA users produce drafts.
  • Block unregistered senders and temporary email accounts before the AI step.
  • Verify senders in batches of 10, so API calls stay low.
  • Return one clear yes/no per email, so n8n needs no extra decision logic.
  • Stop and alert the owner at 100 or more distinct senders in 2 hours.
  • Create one draft reply per learner. Further messages are handled manually.
  • Skip any user who sends more than 10 emails in 24 hours.
3

Scope

This PRD covers everything up to the API result: how n8n collects sender addresses, the verification API, and what n8n does with the answer.

After the API call, the rest of the process stays as already built in n8n. For a verified sender, n8n extracts the learner details, the AI classifies the email, the standard reply is built, a draft is created in the academy mailbox, a copy is forwarded to the owner where the rules require it, and the row is logged in the tracking sheet. Emails forwarded by internal mailboxes keep their current handling; only the learner's address is verified. One draft reply per learner; further messages are handled manually.

Functional requirements

The API returns one answer per email, is_gla_user, with is_active and is_temp to explain it.

How the API verifies an email
  1. Cleans the address (trims spaces, lowercase). A badly formed address returns is_gla_user = false.
  2. Looks the address up in the passes_users table of the website database. If it is not there, the result is false.
  3. Checks the params table for website activity in the last 7 days and sets is_active. No activity means false.
  4. Checks whether the address is a temporary email and sets is_temp. If true, the result is false even when an account exists. The API rejects these itself, for safety.
  5. Only an address in passes_users with is_active true and is_temp false returns is_gla_user = true.
IDRequirementPriority
FR1Accept 1 to 10 email addresses per call. A call with more than 10 or none is rejected with a clear error.Must
FR2Clean each address: trim spaces, lowercase, check the format. A badly formed address returns is_gla_user = false.Must
FR3Mark an address as a GLA user only if it is present in the passes_users table.Must
FR4Count only users with website activity in the last 7 days, checked in the params table.Must
FR5Detect temporary emails: set is_temp = true and return is_gla_user = false, even when a GLA account exists.Must
FR6Return four fields per address: email, is_gla_user, is_active, is_temp. n8n uses is_gla_user to decide.Must
FR7Set is_active from 7 days of params activity and is_temp from the email domain, so n8n can log why an address was rejected.Must
FR8Return a result for every address sent, in the same order, including duplicates.Must
FR9Be read-only and safe to repeat: same input, same answer, nothing changed.Must
FR10Return only the four fields. No other learner data.Should

One endpoint, called by n8n once per batch of up to 10 emails. The name and path are proposals for the API team to confirm.

FieldMeaning
emailThe address that was checked, cleaned (spaces removed, lowercase).
is_gla_userThe final answer n8n uses. True only if the address is in passes_users, is_active is true and is_temp is false.

is_tempTrue if the address is a temporary (disposable) email.
7

n8n integration

The check sits right after the Gmail trigger and before the AI step, so an unverified email costs no AI call, no draft and no forward.

  • Batching. The Gmail trigger checks every 2 hours; its per-check limit is raised from 10 so none are missed. Sender addresses go out in batches of 10, one API call each. Drafts appear up to 2 hours after an email arrives. A duplicate address is sent once.
  • Which address is checked. The sender for a normal email. For mail forwarded by an internal mailbox (info@, contact@, legal@, olympus.oncall@), the learner's address from the forwarded text.
  • Verified. The email continues into the existing flow unchanged.
  • Not verified. The flow stops for that email: no draft, no forward. n8n adds a Gmail label (for example "Not verified") and a row to a "Rejected" tab with the address, subject and API flags, without the body, so the team can review wrongly blocked learners.
  • API down or slow. n8n fails closed: no drafts for that batch. It retries up to 3 times, then holds the emails (unlabelled, picked up on the next run) and alerts the owner. Emails are never lost or drafted without verification.
  • Cost. One API call per batch of up to 10, not one per email.
  • Heavy sender block. If one address sends more than 10 emails in 24 hours, that user is skipped for the next 24 hours and flagged in the Rejected tab.

Every email is checked and none is dropped; each continues or stops on its own is_gla_user result. If no email arrives in the 2 hours, nothing runs: no API call, no AI call, no draft. The next check is 2 hours later.

Volume guard. If 100 or more distinct sender addresses arrive in one 2-hour check, the system stops. n8n makes no API or AI call, creates no drafts and leaves the emails untouched. It emails prajeesh.p@greatlearning.in the number of distinct senders, the time of the check and the most common sender domains, with no email content. The owner reviews the mail (for example a spam flood), removes it, and re-runs the check. The limit of 100 is a starting value and should be adjustable in n8n.

Edge cases and rules

The biggest risk is blocking real learners who write from an address they did not register with, or who have not visited the website in the last 7 days. Every rejection is logged for review.

CaseRule
Learner writes from an address not registered with GLANot verified: no draft. Logged in the Rejected tab for review.
Temporary email registered in GLANot valid: the API returns is_gla_user = false, even though the account exists.
No website activity in the last 7 daysNot valid: is_gla_user = false.
Capital letters, extra spacesCleaned before the check, so they do not cause a mismatch.
Plus-addresses (name+tag@gmail.com) and aliasesTo be decided with the API team.
Email forwarded by an internal mailboxThe learner's address from the forwarded text is verified. If none is found, it goes to the owner for manual handling, as today.
Automatic mail and no-reply addressesFail verification, so they no longer reach the AI.
Spoofed "From" address of a real learnerThe API alone cannot catch this. n8n should also require that Gmail's sender checks (SPF/DKIM) passed.
Same address sending many emailsOne draft per learner; further messages are handled manually. More than 10 emails in 24 hours: the user is skipped and flagged.
9

Success metrics, testing and rollout

The feature is a success when no draft is created for an unverified sender and fewer than 2% of real learners are wrongly blocked.

Metrics
  • Drafts created for unverified senders: 0.
  • Real learners wrongly rejected: under 2% of rejections, checked weekly in the Rejected tab.
  • API calls that fail: under 1%.
  • AI calls and n8n executions saved on rejected mail: reported weekly.
Rollout
  1. Build and test the API with the API team, using test accounts.
  2. Shadow mode for one week: n8n calls the API and logs the result but still drafts every email.
  3. Turn on enforcement once shadow results are acceptable.
  4. Review the Rejected tab weekly for the first month, then monthly.
Test cases
  • A registered learner active in the last 7 days: is_gla_user = true.
  • An address not in GLA: false.
  • A temporary email with a GLA account: false.
  • A user with no website activity in the last 7 days: false.
  • A batch of 10, a batch of 11 (error), and an empty batch (error).
  • Duplicates, capital letters and extra spaces in one batch.
  • API unavailable: no drafts, retries happen, emails are held and the owner is alerted.
  • A forwarded email: the learner's address is checked, not info@.
  • A learner who sends a second message: no second draft; the team handles it manually.
  • A user with 11 emails in 24 hours: the user is skipped and flagged.
